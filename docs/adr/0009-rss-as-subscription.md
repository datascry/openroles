# ADR-0009: RSS feeds as the canonical subscription model

## Status

Superseded by [ADR-0013](0013-no-subscription-model.md)

The site shipped pre-rendered RSS feeds at `/feed.xml`,
`/feed/{ats}.xml`, and `/feed/level/{level}.xml` from Phase 6 onward.
In practice the feeds were rarely subscribed to and the open-standard
RSS argument did not survive contact with how users actually
discovered roles on the site (homepage filter → click apply).
ADR-0013 retires the feeds entirely; the original rationale below is
preserved for future reference if a server-backed deployment ever
revives subscriptions.

## Context

Users who care about a particular slice of the dataset — "remote senior engineering jobs at Greenhouse-hosted companies" — want a way to be notified when new postings match. The traditional pattern is email alerts: an account, a stored filter, a daily/weekly cron, an SMTP integration, deliverability headaches, an unsubscribe page, an account deletion flow.

We are static-only (see ADR-0005). Email alerts would require a backend, a database, a sending integration, and ongoing operational care. None of that earns its keep when an open standard already solves the problem.

## Decision

**RSS feeds are the canonical subscription model.** Users save the URL of a filter into their RSS reader; the reader polls; new matches show up in their existing feed UI. No accounts, no email, no backend, no unsubscribe flow.

### Day-one feeds (statically pre-rendered at build time)

These cover the most common subscription shapes, generated by Astro endpoints reading `bun:sqlite`:

- `/feed.xml` — last 100 jobs across everything
- `/feed/{ats}.xml` — per-ATS firehose (e.g., `/feed/greenhouse.xml`)
- `/feed/level/{level}.xml` — per-level (e.g., `/feed/level/senior.xml`)
- `/feed/role/{slug}.xml` — per-canonical-role (e.g., `/feed/role/security-engineer.xml`)

Format: RSS 2.0 with optional Atom-namespace extensions for richer metadata. Each item carries title, company, ATS source, level, posted-date, link, and a small description.

### Post-ship: arbitrary-filter feeds via Cloudflare Worker

Pre-rendering every plausible filter combination is combinatorially impossible. For arbitrary combinations (e.g., `?q=engineer&ats=greenhouse&level=senior&workplace_type=remote`) a Cloudflare Worker on the free tier renders RSS on demand by reading the public SQLite over HTTP `Range` requests — the same data pipe the main site uses. Pure additive: the static site keeps working without it; the worker only handles arbitrary combinations.

The worker is deferred to a post-ship phase; day-one ships the four canonical feed shapes above.

### Validation

All feeds validate against the [W3C Feed Validator](https://validator.w3.org/feed/) as part of the e2e suite. A broken feed is treated as a CI-blocking regression.

## Consequences

### Positive

- Zero backend on day one. Subscriptions work via existing client-side software the user already has (or chooses).
- Users own their subscription state. They can add, remove, group, archive feeds without touching the project.
- No email deliverability problem. No spam-folder routing. No bounced-address cleanup.
- Privacy: we never see the user's email or their subscription preferences.
- The Worker (post-ship) inherits these properties — it stores no user state.

### Neutral

- RSS is mature but less common in mainstream consumer adoption than 15 years ago. Power users (the most likely audience for a job board aggregator) tend to use feed readers; mainstream users get a usable site even without subscribing.
- Each feed is capped at 100 items to keep file size reasonable. Older items remain queryable via the main UI.

### Negative

- We don't get any usage signal on subscriptions. We can't tell which feed shapes are popular without server-side telemetry, and we won't add that.
- Push semantics (instant notifications) require email or webhooks; RSS readers poll on their own schedule, typically hourly to daily.
- A small fraction of users have never used RSS; we accept that the main UI is the primary surface and RSS is for the engaged subset.

## Alternatives considered

- **Email-alert subscriptions** — adds a database, a cron job, an SMTP integration, deliverability problems, an unsubscribe flow, and ongoing operational responsibility. Much higher cost than RSS for the same outcome.
- **Web Push notifications** — requires a service worker, push subscription endpoints, and per-browser support quirks. Privacy story is murky. Push is a "nudge me right now" pattern; subscription to a job board is closer to "let me know periodically."
- **No subscription mechanism at all** — leaves engaged users without a way to track new matches. RSS is essentially free to provide, so we provide it.
- **Polling the public SQLite from a user's own script** — power-user-only and undocumented; RSS gives the same capability through a standard format.
