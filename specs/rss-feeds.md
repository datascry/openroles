# Spec: RSS feeds

**Version**: 1.0.0

RSS is the canonical subscription mechanism (see [ADR-0009](../docs/adr/0009-rss-as-subscription.md)). Day-one feeds are pre-rendered at build time as static `.xml` files. Arbitrary-filter feeds are deferred to a post-ship Worker.

## Day-one static feeds

Generated by Astro endpoints under `site/src/pages/feed/`, reading `bun:sqlite` at build time:

| Path | Contents | Cap |
|---|---|---|
| `/feed.xml` | Last N jobs across the entire dataset | 100 |
| `/feed/{ats}.xml` | Last N jobs for a single ATS | 100 |
| `/feed/level/{level}.xml` | Last N jobs at a single level | 100 |
| `/feed/role/{slug}.xml` | Last N jobs for a canonical role slug (`security-engineer`, `data-scientist`, …) | 100 |

`{ats}` is the closed `ATSId` set. `{level}` is the closed `Level` set. `{slug}` is a curated set of canonical roles maintained in `shared/src/constants.ts` — any change to the set bumps the spec version.

## Feed format

RSS 2.0 with the `atom` namespace for richer metadata.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<rss version="2.0" xmlns:atom="http://www.w3.org/2005/Atom">
  <channel>
    <title>openroles — {scope}</title>
    <link>{site_url}/{scope-path}</link>
    <description>{human-readable scope description}</description>
    <language>en-US</language>
    <lastBuildDate>{built_at, RFC 822}</lastBuildDate>
    <atom:link href="{absolute_feed_url}" rel="self" type="application/rss+xml" />
    <generator>openroles</generator>
    <ttl>1440</ttl>  <!-- minutes; matches our 24h refresh cadence -->

    <item>
      <title>{Job.title} — {Job.company}</title>
      <link>{Job.url}</link>
      <guid isPermaLink="true">{Job.url}</guid>
      <pubDate>{Job.posted_at, RFC 822}</pubDate>
      <description><![CDATA[
        <p><strong>{Job.company}</strong> · {Job.location_text or "Location not specified"}</p>
        <p>Level: {Job.level or "Not classified"} · Workplace: {Job.workplace_type or "Not specified"}</p>
        <p>{Job.description_excerpt}</p>
      ]]></description>
      <category>{Job.ats}</category>
      <category>{Job.level}</category>
    </item>
    <!-- ... up to 100 items, sorted by posted_at DESC ... -->
  </channel>
</rss>
```

## Item shape

Per item:

- **`title`** — `"{Job.title} — {Job.company}"`. Job title leads so feed-reader truncation preserves the most informative part.
- **`link`** — `Job.url` (the apply URL on the source ATS).
- **`guid`** — same as `link`, with `isPermaLink="true"`. Stable across feed regenerations.
- **`pubDate`** — `Job.posted_at` if present, else `Job.first_seen_at`. RFC 822 format (e.g., `Mon, 26 Apr 2026 00:00:00 GMT`).
- **`description`** — HTML wrapped in CDATA. Includes company, location, level, workplace type, and the description excerpt. Always includes structural HTML so feed readers render meaningful content.
- **`category`** — multiple, including the ATS and the level. No free-text categories — only values from the closed enums.

## Build-time invariants

- Every static feed validates against the [W3C Feed Validator](https://validator.w3.org/feed/). A non-conforming feed fails the build.
- Feed files are content-hashed in their HTTP `Last-Modified` header, derived from the latest `Job.last_seen_at` they contain.
- Empty feeds are still emitted (with `<channel>` and zero items) — never a 404. This makes subscriber bookmarks stable.
- `<lastBuildDate>` matches `Manifest.built_at` exactly; never older.
- Maximum file size: ~50 KB per feed (100 items × ~500 bytes/item). Larger feeds are a regression.

## Sort and selection

For all day-one feeds, items are sorted by `posted_at DESC`. Within a tie on `posted_at`, sort by `first_seen_at DESC`, then by `id ASC` for determinism.

Selection criteria:

- `/feed.xml`: top 100 by `posted_at DESC` across the whole table.
- `/feed/{ats}.xml`: top 100 by `posted_at DESC` filtered by `ats = ?`.
- `/feed/level/{level}.xml`: top 100 by `posted_at DESC` filtered by `level = ?`.
- `/feed/role/{slug}.xml`: top 100 by `posted_at DESC` filtered by a canonical role mapping (defined in `shared/src/role-canonicalization.ts`).

Items with `posted_at` older than 90 days are excluded from feeds — feed readers should not be flooded with stale postings on a fresh subscription.

## Post-ship Worker (arbitrary filters)

A Cloudflare Worker reads the public SQLite over HTTP `Range` and renders RSS for any filter combination on demand. The query string uses the same parameter names as the filter UI (see [filter-ui.md](filter-ui.md)):

```
GET /feed/?q=engineer&ats=greenhouse&level=senior&wt=remote
```

Same feed format and item shape as day-one feeds. Cap remains 100 items. Worker enforces an upper bound on parameter cardinality (e.g., max 6 ATSes selected) to keep query cost bounded.

The Worker stores no user state. Each request is independent. It exists purely to spare us the combinatorial explosion of pre-rendering every plausible filter combination.

## Headers

Static feeds and Worker-rendered feeds both ship:

- `Content-Type: application/rss+xml; charset=utf-8`
- `Cache-Control: public, max-age=3600` — one hour. RSS readers poll at varying cadences; this aligns with `ttl` of 1440 minutes (24h) without forcing minute-fresh polling on every reader.
- For static feeds: `ETag` derived from the file content hash.
- For Worker feeds: `ETag` derived from the latest `Job.last_seen_at` matching the filter.

## Rejection cases

- A request to `/feed/{ats}.xml` for an unknown `{ats}` returns HTTP 404 (static), or 400 (Worker).
- A Worker request with > 6 selected values for any multi-select filter returns 400.
- A Worker request with a malformed `since` value falls back to the default (no time filter).

## Test discipline

- Each static feed shape has a build-time assertion: the rendered XML validates and contains the expected number of items.
- A snapshot test pins the structural shape of one item (locked across builds; updates require a spec version bump).
- A property test asserts that any subset of the dataset, when rendered, validates as RSS 2.0.
